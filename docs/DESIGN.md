# 设计说明

本文记录 `moyu-index_28` 的指标选择理由与计分推导，方便后续调整参数时保持一致性。

## 1. 设计目标

1. **可量化**：四项输入都能被用户自己数出来，不依赖任何埋点或联网采集。
2. **可解释**：分数由明确公式得出，任何一个分数都能反推是哪一项拉高的。
3. **可复现**：同样的输入永远得到同样的分数与语录，不引入随机数。
4. **零依赖**：只使用 Python 标准库，任何装了 Python 的机器都能跑。

## 2. 为什么是这四项指标

| 指标 | 选它的理由 | 不选更「准」的指标的原因 |
| --- | --- | --- |
| 窗口切换次数 | 最能反映注意力漂移，且系统自己就能看到 | 采集需要权限，涉及隐私 |
| 单次最长摸鱼时长 | 反映摸鱼的「深度」，而非频次 | 难以自动测量，只能靠自述 |
| 遁走次数 | 反映摸鱼的「仪式感」，也是打工人最通用的行为 | — |
| 真实工作占比 | 作为锚点，避免前三项高但实际没耽误事时分数失真 | — |

四项分别对应「浅层摸鱼」「深层摸鱼」「物理摸鱼」「心理摸鱼」，覆盖了常见场景。

## 3. 归一化

对计数类指标，设上限 `cap`，归一化函数为：

```
n(x) = min(max(x / cap, 0), 1)
```

超过上限的部分按 1 计，因此 `switch=999` 与 `switch=120` 结果相同。上限取值依据：

- 窗口切换 120 次 ≈ 一天 8 小时每 4 分钟切一次，已经是上线；
- 单次连续摸鱼 180 分钟 ≈ 半天，再长就没额外区分意义；
- 遁走 10 次 ≈ 每个工作小时一次，超过即为满分。

## 4. 加权

```
score = 100 × ( 0.30·n(switch) + 0.25·n(idle) + 0.20·n(escape) + 0.25·(1 - real_work) )
```

然后用 `round()` 取整，并夹在 `[0, 100]` 内。

权重和为 `0.30 + 0.25 + 0.20 + 0.25 = 1.0`，因此四项全部拉满时恰好等于 100，
全部为零时恰好等于 0，不会出现溢出或不足 100 的情况。权重分配的原则是
「自动可测的指标权重更高」，把 `switch` 放在首位。

## 5. 等级与文案

等级用阈值表实现，从上往下匹配第一个满足的区间：

```python
LEVELS = ((75, "赛博隐士"), (50, "摸鱼带师"), (25, "正常打工"), (0, "卷王本王"))
```

语录的选取使用 `score % len(bucket)`，而不是随机数，这样：
同一个分数一定得到同一句话，测试可以断言输出，也方便用户复现截图。

## 6. 边界情况处理

| 情况 | 处理方式 |
| --- | --- |
| 输入负数 | `compute_score` 抛 `ValueError`；交互模式回落默认值 |
| 输入非数字 | 交互模式提示后回落默认值 |
| `real_work_ratio` 超出 0~1 | 抛 `ValueError`，CLI 返回退出码 2 |
| `width <= 0` | `bar()` 抛 `ValueError` |
| 用户按 Ctrl+D | 捕获 `EOFError`，回落默认值，不打印 traceback |
| 非 TTY（管道调用） | 跳过交互，直接使用命令行参数 |

## 7. 分层结构

```
cli.py     负责输入输出、参数解析、错误提示
render.py  负责把数字变好看
core.py    纯函数，不做 IO，可被任何前端复用
quotes.py  纯数据
```

`core.py` 里没有任何 `print` 与 `input`，因此可以安全地被 Web 服务或 GUI 复用；
这也是本项目能保持高测试覆盖率的原因。
